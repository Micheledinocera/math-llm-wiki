# Math LLM-Wiki — rules for the agent

This repository is a wiki of mathematics maintained by you, the agent, from which the author writes articles. You maintain the connective tissue (notation, dependencies, provenance, epistemic status); the author keeps the mathematical judgment.

The design and its reasons are in `docs/spec-v0.1.md` (Italian). This file is the binding version: if the two disagree, follow this file and point out the difference to the author.

## Layout

```text
raw/sources/        external sources, immutable (Markdown conversions of PDFs, lecture notes)
raw/sources/_registry.md   source registry: id, citation, reliability, file, ingest date
raw/ideas/          the author's ideas, dated: YYYY-MM-DD-title.md
wiki/index.md       every page with a one-line summary: always start here
wiki/notation.md    binding notation and conventions
wiki/open-questions.md     open questions, one q- section each
wiki/definitions/   def-
wiki/results/       lem-, prop-, thm-, conj-
wiki/examples/      ex-, cex-
wiki/concepts/      con-
wiki/sources/       src-, one page per source
articles/<slug>/    plan.md, draft.md, build/ (generated by export, never edited by hand)
templates/          one template per page type, plus the article plan
log/changelog.md    log of your operations and the "ready for verification" list
scripts/lint.py     mechanical checks
```

## Principles

1. **Raw is immutable.** You read `raw/` and never change it (the only exception: the registry, see rule 1). Sources are the ground truth.
2. **No statement without provenance.** Every statement in the wiki names the `raw/` file or the wiki page it comes from.
3. **The human promotes the status.** You may propose a proof; only the author marks it verified, fully or partly.
4. **One source of truth for notation.** `wiki/notation.md` binds the wiki and the articles.
5. **The wiki is the warehouse, the article is the shop window.** Articles draw from the wiki; a new result is born in the wiki and then enters an article.
6. **Everything is text.** Markdown with inline `$...$` and display `$$...$$` LaTeX, readable in Obsidian, versioned with git. Articles stay Markdown; `.tex` is generated only on export.
7. **One operation at a time, human in the loop.** Ingest and compile process one source or one idea per run and end with a summary of the changes.
8. **English.** Wiki, articles, frontmatter and changelog are in English, even when sources or ideas are in other languages.

## Pages

File names are stable slugs in lowercase English with hyphens (`def-compact-space.md`, `thm-baire.md`). The slug is the page id and the target of `[[slug]]` links (Obsidian-compatible). Link with the bare slug, never with a path: `[[thm-baire]]`, `[[thm-baire|Baire's theorem]]`, `[[open-questions#q-slug]]`. Never rename a slug: other pages, articles and the author's notes point to it.

| Type | Folder | Slug prefix | Content | Template |
| --- | --- | --- | --- | --- |
| definition | `definitions/` | `def-` | statement, minimal examples, variants in the literature | `templates/definition.md` |
| result | `results/` | `lem-`, `prop-`, `thm-`, `conj-` | statement, proof or sketch, dependencies | `templates/result.md` |
| example | `examples/` | `ex-`, `cex-` | construction, what it illustrates or refutes | `templates/example.md` |
| concept | `concepts/` | `con-` | discursive synthesis, connections | `templates/concept.md` |
| source | `sources/` | `src-` | summary of the source, extracted pages, notation map | `templates/source.md` |
| question | `open-questions.md` | `q-` (heading anchor) | question, motivation, attempts | `templates/question.md` |

Always start a page from its template. Frontmatter fields:

- `id`: the slug, equal to the file name; `type`: the type above; `updated`: date of the last operation that changed the page.
- `provenance`: list, never empty. Each entry is a `raw/` path, with `#<statement>` when it points inside a source (`raw/sources/huang2019.md#theorem-1.1`, `raw/sources/horn2013.md#p-242`), or the slug of a wiki page it is derived from.
- `depends_on`: slugs the statement or the proof uses. `used_in`: `articles/<slug>` of the articles that use the page; `/draft` maintains it.
- `notation_checked`: `true` only when every symbol on the page is in `notation.md` with the same meaning.
- results: `kind` (`lemma` | `proposition` | `theorem` | `conjecture`, matching the prefix), `status` (see below), `unchecked_steps` (only for `partial`: the steps not yet checked).
- examples: `kind` (`example` | `counterexample`, matching `ex-` / `cex-`), `illustrates` and `refutes` (slugs).
- sources: `source_id`, `citation`, `reliability`, `ingested`.

**Granularity (open, to be tested):** create a page only for results that are reused. A technical lemma used once stays inside the proof that uses it.

**Source vs interpretation:** the body states what the provenance says. Your own reading, comparisons, guesses go in the **Notes** section, in a paragraph starting `*Interpretation (agent):*`.

**Source ids:** `<firstauthor><year>` in lowercase, with `a`, `b`… on clashes (`huang2019`). Source file `raw/sources/<id>.md`, page `wiki/sources/src-<id>.md`.

**Notation page:** a table `Symbol | Meaning | LaTeX macro | Introduced in | Notes` plus a list of general conventions. The macro column is what export will use.

## Epistemic statuses

Every result has exactly one status.

| Status | Meaning | Who sets it | Usable in an article |
| --- | --- | --- | --- |
| `conjecture` | believed true, no proof | agent or author | only as a declared conjecture |
| `sketch` | proof idea with missing steps | agent or author | no |
| `proposed` | complete proof written by the agent, not checked | agent only | no |
| `partial` | proof checked by the author only in part; `unchecked_steps` lists the rest | author only | yes, with a lint warning |
| `verified` | complete proof checked by the author | author only | yes |
| `cited` | proved in a source in `raw/sources/`, with a precise reference | agent, confirmed by the author | yes, with citation; warning if the source is `preprint` or `informal` |
| `refuted` | false; the page links the counterexample | agent or author | no |

Promotion rules:

- you never set `verified` or `partial`; you can only report that a result is ready for verification;
- `cited` needs the statement number in the source (theorem, page) in the provenance anchor;
- when a result others depend on goes down in status, report every page and article that uses it (follow `depends_on` and `used_in`);
- a result's status never exceeds the status of its weakest dependency. Strength order: `refuted` < `conjecture` < `sketch` < `proposed` < `partial` < `cited` = `verified`. `scripts/lint.py` computes it.

### Source reliability

How settled a result is in the community is a property of the source, so it is a separate axis from the status. Every source has `reliability` in the registry and on its `src-` page.

| Level | Examples | Effect on `cited` results |
| --- | --- | --- |
| `standard` | textbooks, monographs, classical results | none |
| `refereed` | papers published in peer-reviewed journals | none |
| `preprint` | arXiv not yet published, recent papers | lint warning when used in an article |
| `informal` | lecture notes, slides, blogs, personal communications | lint warning; verification recommended |

A `cited` result from a `preprint` or `informal` source can move to `partial` or `verified` when the author checks its proof. When a source changes level (a preprint gets published), the author updates the registry and the `src-` page, and lint recomputes the warnings.

## Operations

The author runs them explicitly, one skill each, in `.claude/skills/`. Each skill has the detailed steps.

| Command | What it does | Changes |
| --- | --- | --- |
| `/ingest <file>` | brings one source into the wiki: registry row, `src-` page, pages with status `cited` | wiki, registry, changelog |
| `/compile <idea>` | brings one idea into the wiki: pages as `conjecture` or `sketch`, provenance in `raw/ideas/` | wiki, changelog |
| `/query <question>` | answers from the wiki (index first, then pages), citing slugs; offers to save new material | nothing, unless the author accepts a new page |
| `/draft <article>` | works on `articles/<slug>/` from its plan, with allowed results only; updates `used_in` | article, `used_in`, changelog |
| `/lint` | health report: `scripts/lint.py` plus the judgment checks (notation, order of definitions) | nothing, unless the author accepts fixes |
| `/export <article>` | *planned, not in v0.1*: `.tex` and `.bib` in `articles/<slug>/build/` | — |

**Lint report:** errors are statuses not allowed in an article, notation conflicts, broken or circular dependencies, incoherent statuses, missing provenance or index entries. Warnings are `partial` results, `cited` results from `preprint`/`informal` sources, open gaps, orphan pages. Warnings do not block, but their full list must be shown before an article is closed.

**Comments in drafts:** `<!-- check: [[slug]] ... -->` next to every use of a `partial` result or of a `cited` result from a `preprint`/`informal` source; `<!-- gap: [[slug]] ... -->` where the article needs a result that is not usable yet.

## Rules

1. Never modify, rename or delete anything in `raw/`. Single exception: `raw/sources/_registry.md`, where `/ingest` appends one row per source, and where you change `reliability` only on the author's request.
2. Every statement you write in the wiki has a provenance in the frontmatter. If you do not know where it comes from, do not write it.
3. Never set the statuses `verified` or `partial`. When a `proposed` proof looks complete to you, add it to the *Ready for verification* list in `log/changelog.md`.
4. Never invent references: theorem number, page and citation must appear in the source.
5. Before introducing a symbol, check `notation.md`. If it is missing, propose an entry and add it only after the author's ok; if it conflicts, report it and stop.
6. Ideas in `raw/ideas/` are not facts. Never promote them to `cited`.
7. Always separate what the source says from your interpretation: the latter goes in **Notes**, marked `*Interpretation (agent):*`.
8. After every operation that changes the wiki, update `wiki/index.md` and `log/changelog.md`, then run `python scripts/lint.py` and fix the mechanical errors you introduced.
9. In an article use `cited`, `verified` or `partial` results; for `partial` ones, and for `cited` ones from `preprint` or `informal` sources, add a `<!-- check: ... -->` comment in the draft. For any other status, report the gap (`<!-- gap: ... -->`) instead of filling it.
10. If a request contradicts these rules, ask the author for confirmation.

More rules that follow from these:

- **Conflicts** between a source or idea and an existing page: keep the existing text, record the point in the page's Notes as `*Conflict:*` with both provenances, and list it in the summary. Never resolve it on your own.
- **No mathematics from memory as fact.** You may use general knowledge to read a source or to answer a query, but what enters the wiki needs a provenance. If something useful has no source in `raw/`, suggest a source to add.
- **Git:** operations do not commit. They end with a summary and a suggested commit message (`ingest: huang2019`, `compile: 2026-10-06-title`, `draft: <slug>`); commit only when the author asks.

## Changelog

`log/changelog.md` has two sections. *Ready for verification* is a maintained list: add a line when a `proposed` proof looks complete, remove it when the author changes the status. *Log* is append-only, newest first, one entry per operation:

```markdown
### YYYY-MM-DD — ingest raw/sources/<id>.md
- Created: [[def-...]], [[thm-...]]
- Updated: [[def-...]] (provenance)
- Conflicts: none
- Notation proposals: <symbol> for <meaning> (accepted / pending)
- Notes: results the source quotes without proving, not added; anything skipped
```
